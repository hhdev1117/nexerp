# 전사 권한관리 구현·운영 상태

## 구현 범위

관리자 전용 `/settings/enterprise-access`에서 회사별 정책을 작성하고 실제 적용할 수 있다.

- 레벨 1~5의 메뉴·행동·범위별 권한, 직급·직책 매칭, 적용 기간, 사용자 직접 등급 지정.
- 기존 계정과 회사 연결, 업무 역할, 개인별 허용·거부 예외 및 정책 미리보기.
- 초안 저장과 실제 발행 분리, 변경 사유·감사 기록·버전 충돌 검사, 이전 발행본 복원.
- 서버가 로그인 사용자와 현재 날짜를 기준으로 반환한 회사 목록·메뉴 권한에 따른 회사 전환과 접근 제어.
- 회사·사업장 조회·등록·수정에 대한 서버 RLS 및 화면 행동 권한 적용.

정책은 `enterprise_access_policies`, 초안 감사 기록은 `enterprise_access_policy_audit`, 불변 발행본은 `enterprise_access_publications`에 저장한다. 초안을 수정해도 발행 전까지 실제 권한은 바뀌지 않는다. 사용자·직급·직책 연결은 정책 스냅샷이며 인사 원장 자체는 아니다.

## 적용과 복구

발행 이력이 전혀 없는 환경은 기존 권한을 유지한다. **최초 발행부터 전사 권한 전환이 시작된다.** 일반 사용자는 발행된 회사 정책에 유효하게 연결되어야 접근할 수 있다. 미발행 회사나 연결되지 않은 사용자는 기존 권한으로 우회할 수 없으므로 최초 발행 전에 회사별 정책과 계정 연결을 준비해야 한다.

실제 적용은 저장한 초안, 변경 사유, 영향 확인을 요구한다. 되돌리기는 이전 발행본을 새 버전으로 복원하며 권한 강제를 해제하지 않는다. 첫 발행에는 이전 버전이 없으므로 되돌리기를 사용할 수 없다.

기술 관리자의 계정관리·권한관리 등 복구 경로는 유지한다. 레벨 5만으로 기술 관리자 권한을 얻지는 않는다. 비활성 회사의 복구는 명시적으로 허용된 회사 설정 조회·수정 권한으로 가능하며 다른 업무 접근은 계속 차단한다. 관리자 정책 편집에는 비활성 회사·사업장 메타데이터도 제공한다.

회사 전환 시 편집 중인 업무 화면의 입력 유실을 확인하고 접근 문맥을 다시 불러온다. 권한 조회 실패 시 업무 접근을 차단하며 기존 권한으로 대체하지 않는다. 관리자 정책 편집 화면의 초안은 권한 새로고침 중에도 유지한다.

## 데이터베이스 적용

마이그레이션 순서는 `20260914000100_add_companies_and_sites.sql`, `20260914000200_enterprise_access_policy.sql`, `20260914000300_enterprise_access_activation.sql`이다. 001이 적용된 환경에는 002와 003을 순서대로 적용한다. 2026-09-15 운영 프로젝트 `mehhrnbaiojivesnobpv`에 002와 003을 적용하고 최신 Worker를 배포했다. 정책 발행본은 아직 0건이므로 최초 발행 전까지 기존 권한 호환 모드가 유지된다.

정책 저장·발행·복원은 활성 기술 관리자 및 AAL2를 검증하는 RPC로 제한한다. 클라이언트에 직접 정책 쓰기 권한은 없다. 런타임 RPC는 임의 사용자 ID를 받지 않고 로그인 계정으로 판정하며 전체 정책을 노출하지 않는다. 회사 신규 생성은 기술 관리자 작업으로 유지한다.

새 메뉴를 추가할 때 서버 리소스 목록과 정책을 함께 검토한다. 등록되지 않은 리소스, 존재하지 않는 계정, 다른 회사 사업장, 겹치는 매핑 기간은 저장하지 않는다. 날짜는 YYYY-MM-DD 또는 null이며 빈 날짜는 저장소에서 null로 정규화한다.

## 후속 범위

직원 명부와 날짜별 주 소속·퇴사 발령에 따른 권한 연계를 구현했다. 겸직 직책 권한은 기본 레벨을 바꾸지 않고 대상 부서 범위에만 추가된다. [직원 명부·발령 안내](hr-ledger.md)와 [겸직과 부서 범위 권한 안내](hr-secondary-assignments.md)를 참조한다. 업무 역할의 독립 유효기간, 민감 필드 권한 및 실제 문서 결재 상태 검증은 후속 구현이다. 다른 업무 화면은 아직 데모 또는 공용 화면이므로 이번 메뉴 제어가 해당 업무 데이터의 서버 보안을 완성했다는 의미는 아니다. 업무 테이블을 구현할 때 각 RLS/RPC에 `private.enterprise_granted_for_target` 판정을 연결해야 한다.

## 검증

전체 ESLint와 production build를 확인한다. 발행 화면과 회사 선택기는 1440px/375px에서 격리된 예시 데이터로 렌더링해 가로 넘침과 페이지 오류가 없음을 확인했다. `supabase/tests/enterprise_access_policy_rls.test.sql` 및 `enterprise_access_activation_rls.test.sql`의 전체 pgTAP 실행은 별도 Supabase 환경에서 필요하다.
