# 전사 권한관리 구현·운영 상태

## 이번 구현

관리자 전용 `/settings/enterprise-access`에서 회사를 선택한 뒤 다음 정책을 저장하고 검토할 수 있다.

- 레벨 1~5의 메뉴·행동·범위별 권한. 같은 행동에 여러 범위 지정 가능.
- 직급·직책 코드와 등급 연결, 적용 기간, 직책 우선 및 직접 등급 지정.
- 기존 계정 선택을 통한 회사별 사용자 연결, 업무 역할, 개별 allow/deny.
- 기준일·사용자·자료 대상·행동에 대한 로컬 정책 판정과 이유.
- 회사별 정책 버전, 변경 사유, 변경 전후 감사 기록, 동시 저장 충돌 차단.

저장소는 `enterprise_access_policies`, 감사 원장은 `enterprise_access_policy_audit`다. 문서 기반 정책을 하나의 RPC 트랜잭션으로 저장한다. 이 단계의 사용자·직급·직책 연결은 전환 준비용 정책 스냅샷이며 인사 원장 자체가 아니다.

## 아직 적용하지 않은 범위

기존 `admin/approver/user` 메뉴 및 서버 정책은 유지된다. 이 화면의 저장은 기존 업무 API에 새 권한을 즉시 적용하지 않는다. 화면에도 '권한 전환 준비'와 기존 권한 미전환 상태를 표시한다.

전체 설계 중 영속 인사 원장·복합 FK 연결, 발령 자동 연계·겸직, 업무 역할의 독립적 유효기간, 정책 발행 및 모듈별 서버 강제 전환, 시스템 권한 위임·마지막 관리자 보호, 자료별 민감 필드 분리는 후속 구현 범위다. 미리보기는 계정 활성·AAL2·모듈 사용을 가정하며 실제 문서 결재·배정·조직 트리 상태를 대신하지 않는다.

## 데이터베이스 적용

현재 회사·사업장 마이그레이션 이후 `supabase/migrations/20260914000200_enterprise_access_policy.sql`을 적용한다. 이 작업에서는 운영 데이터베이스에 적용하거나 배포하지 않았다. 테이블이 없는 환경에서는 화면이 저장 실패를 표시하며 데모 데이터로 대체하지 않는다.

RLS는 기존 `private.is_admin()`의 활성 계정·AAL2 검증을 재사용한다. 클라이언트에는 직접 insert/update/delete grant가 없고 저장 RPC만 실행할 수 있다. 현재 기술 관리자는 여러 회사의 전환 설정을 관리한다. 레벨 5라는 이유로 실제 기술 관리자 권한을 얻지 않는다.

등록 리소스 목록은 마이그레이션의 명시적인 목록이다. 새 메뉴를 추가할 때 목록과 신규 정책 권한을 함께 검토한다. 임의 리소스, 존재하지 않는 계정, 다른 회사 사업장, 겹치는 매핑 기간은 저장되지 않는다. 날짜는 YYYY-MM-DD 또는 null이며 UI의 빈 날짜는 저장소에서 null로 정규화한다.

## 검증

2026-09-14 최종 검증: Vitest 51개 파일·646개 테스트 통과, ESLint 통과, production build 성공. 1440px/375px에서 실제 Vue 화면의 네 탭을 격리된 예시 데이터로 렌더링해 가로 넘침과 페이지 오류가 없음을 확인했다.

Vitest의 도메인·리포지토리·화면·라우터 검증과 전체 회귀 검사, ESLint 및 production build를 수행한다. `supabase/tests/enterprise_access_policy_rls.test.sql`은 전체 Supabase와 pgTAP 환경에서 실행할 테스트다.

로컬 보조 검증은 PGlite PostgreSQL에 신규 마이그레이션을 실행해 20개 시나리오를 검증했다. auth.uid/private.is_admin과 기존 테이블의 필요한 모양만 제공했으므로 전체 Supabase Auth나 이전 마이그레이션 통합 검증을 뜻하지 않는다. 전체 pgTAP 실행은 별도 환경에서 필요하다.
