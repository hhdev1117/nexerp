# 겸직과 부서 범위 권한 운영 안내

## 적용 순서

기존 마이그레이션을 파일명 순서대로 적용한 뒤 `20260915000800_hr_employment_cycles.sql`, `20260915000900_hr_secondary_assignments.sql`을 적용한다. 009는 최초 직원 생성 시 1회차 고용 이력도 함께 생성하도록 기존 RPC를 보완한다. 이번 작업에서는 운영 DB 적용과 앱 배포를 수행하지 않았다.

## 업무 규칙

겸직은 직원과 고용 회차에 연결되며 사업장, 부서, 직책, 시작일과 선택적 종료일을 저장한다. 개인 직급은 주 소속의 직급을 공통으로 사용하므로 겸직에 별도 직급을 저장하지 않는다. 기간은 서울 날짜의 `[시작일, 종료일)`로 계산한다.

같은 고용 회차에서 같은 부서의 겸직 기간은 겹칠 수 없다. 서로 다른 부서는 동시에 겸직할 수 있다. 겸직 부서는 해당 날짜의 주 소속 부서와 달라야 하며, 주 소속 이동으로 이 규칙을 깨는 발령도 서버가 거부한다. 모든 기간은 고용 회차 안에 있어야 한다.

시작 전 겸직은 취소 사유와 함께 취소할 수 있다. 시작된 겸직은 종료일과 종료 사유를 기록한다. 퇴사 발령 시 진행 중인 겸직은 퇴사일에 종료되고 아직 시작하지 않은 겸직은 취소된다. 퇴사 발령을 취소해도 이미 기록된 겸직 종료·취소는 자동으로 되돌리지 않는다.

## 권한 범위

겸직 직책 매핑은 사용자의 기본 레벨을 바꾸지 않고 추가 권한만 만든다. 직책 권한의 `company`와 `organization_tree` 범위는 겸직 부서와 현재 활성 하위 부서로 제한된다. `organization`은 겸직 부서만, `site`는 겸직 사업장 안의 해당 조직 트리만 허용한다. `self`와 `assigned` 권한은 겸직에서 파생하지 않는다. 같은 행동에 적용되는 개인 거부 규칙은 기본·역할·겸직 허용보다 우선한다.

영속 업무 RPC는 회사 단위 판정만으로 처리하지 말고 `private.enterprise_granted_for_target(company, resource, action, site, department)`를 호출해야 한다. `enterprise_explain_scoped_access`는 기본 레벨, 대상, 허용 출처와 거부 규칙을 확인하는 진단용 RPC다.

겸직 조회·등록·종료는 인사 기본 모듈이 사용 상태이고 `hr.core` 회사 전체 조회·수정 권한이 있어야 한다. 예정 취소는 진행 건 정리 상태에서도 가능하다. 읽기 전용과 사용 중지에서는 취소할 수 없다. 미래 시작일이나 종료일이 남아 있으면 모듈의 진행 건수에 한 건으로 포함된다.

## 데이터 보호

`hr_secondary_assignments`는 RLS가 활성화된 RPC 전용 원장이다. `authenticated`, `anon`, `public`에는 테이블 직접 권한이 없다. 등록·종료·취소는 직원 행과 고용 회차를 잠그고 직원 버전 및 겸직 버전을 검사한다. 작성자, 종료자, 취소자, 시각과 사유를 보존한다.

로컬 PGlite 검증은 Auth 함수를 대체한 단일 백엔드 검사다. 실제 Supabase 환경에서는 마이그레이션 적용 후 RLS, 함수 실행 권한, 두 세션의 잠금 경합을 추가 확인한다.

## 로컬 검증 기록

2026-09-15 기준 전체 Vitest 72개 파일·814개 테스트, ESLint, 프로덕션/PWA 빌드를 통과했다. HR PostgreSQL 런타임 검증은 겸직 34개를 포함해 총 249개 단언을 통과했다. 실제 컴포넌트는 1440×1000, 375×900, 812×375에서 등록 검토·진행 중 종료·예정 취소를 확인했으며 페이지 오류와 가로 넘침이 없었다. 375px 화면에서 입력·버튼 최소 높이 44px와 모든 입력의 연결된 라벨을 확인했다.
