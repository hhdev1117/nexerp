# 영문 소문자·숫자 ID 인증 전환 설계

## 목표

NEXERP의 모든 사용자 계정을 이메일 주소 대신 영문 소문자와 숫자로 구성된 로그인 ID로 관리한다. 기존 Supabase Auth 세션, 비밀번호 인증, TOTP 2단계 인증, RLS 정책은 유지한다. 첫 관리자 계정도 같은 규칙으로 생성한다.

## 로그인 ID 규칙

- 정규식: `^[a-z0-9]{4,20}$`
- 허용 문자: 영문 소문자 `a-z`, 숫자 `0-9`
- 숫자로 시작 가능
- 대문자, 한글, 공백, 특수문자 불가
- 대소문자 변환 없이 입력값을 그대로 검증
- 전체 사용자 사이에서 중복 불가

## 선택한 인증 방식

Supabase Auth가 이메일/비밀번호 인증을 계속 담당하되, 애플리케이션은 로그인 ID를 내부 가상 이메일로 결정적으로 변환한다.

```text
login_id: admin01
internal email: admin01@nexerp.internal
```

가상 이메일은 인증 공급자와 서버 코드에서만 사용한다. 로그인 화면, 계정 관리 화면, API 응답, 프로필 표시에는 노출하지 않는다. 이 방식은 별도 비밀번호 저장소를 만들지 않으면서 Supabase의 세션 갱신, 비밀번호 변경, TOTP, 관리자 API를 그대로 활용한다.

## 데이터 모델

`public.profiles`에 `login_id text not null`을 추가하고 고유 인덱스와 형식 제약을 둔다. 기존 `email` 열은 Supabase Auth 연동과 이전 마이그레이션 호환성을 위해 당분간 유지하되 애플리케이션 API 및 UI에서는 제거한다.

새 사용자 트리거는 다음을 검증한다.

1. 관리 API가 `nexerp_provisioned = true` 메타데이터를 설정했는지 확인한다.
2. `login_id` 앱 메타데이터가 ID 형식에 맞는지 확인한다.
3. Auth 이메일이 `<login_id>@nexerp.internal`과 정확히 일치하는지 확인한다.
4. 검증된 ID로 프로필을 생성한다.

## 인증 흐름

### 로그인

로그인 화면은 `이메일` 대신 `아이디`를 입력받는다. 클라이언트는 형식을 검증한 후 내부 변환 함수로 가상 이메일을 만들고 Supabase `signInWithPassword`를 호출한다. 인증 실패 메시지는 계정 존재 여부를 노출하지 않도록 `아이디 또는 비밀번호가 올바르지 않습니다`로 통합한다.

### 비밀번호 변경과 TOTP

현재 세션 사용자의 Auth 이메일은 내부 재인증에만 사용한다. UI에는 ID만 표시한다. 기존 TOTP 등록·검증·초기화 흐름과 AAL2 강제 정책은 유지한다.

### 관리자 계정 관리

계정 생성 폼과 API는 `email` 대신 `loginId`를 받는다. Worker는 ID를 검증하고 가상 이메일을 생성해 Supabase Admin API로 사용자를 만든다. 프로필 API 응답과 목록 검색도 `loginId`를 사용한다. 중복 오류는 `login_id_exists`로 통일한다.

## 첫 관리자 부트스트랩

일반 관리자 API는 이미 활성화된 관리자 세션을 요구하므로 첫 계정은 일회성 운영 스크립트로 생성한다.

1. 운영자가 확정한 로그인 ID와 임시 비밀번호를 입력한다.
2. 스크립트가 Supabase Admin API로 확인된 Auth 사용자를 생성한다.
3. 생성된 프로필을 `admin`, `is_active = true`로 승격한다.
4. 사용자는 첫 로그인 후 TOTP를 등록한다.
5. 임시 비밀번호는 저장하거나 출력 로그에 남기지 않는다.

스크립트는 활성 관리자 계정이 이미 있으면 기본적으로 중단해 중복 부트스트랩을 방지한다.

## 마이그레이션 전략

현재 새 Supabase 프로젝트에는 사용자 데이터가 없으므로 기존 계정 변환은 필요하지 않다. 새 마이그레이션은 `login_id` 열, 제약, 고유 인덱스, 갱신된 사용자 생성 트리거를 원자적으로 적용한다. 향후 기존 데이터가 있는 환경에 적용할 경우 별도 백필 마이그레이션이 필요하며 이번 범위에는 포함하지 않는다.

## 보안

- 실제 비밀번호는 Supabase Auth만 저장한다.
- 가상 이메일 도메인은 외부 메일 송수신에 사용하지 않는다.
- 가입은 계속 비활성화하고 사용자 생성은 관리자 Worker API로만 수행한다.
- Worker의 `service_role` 키는 Cloudflare Secret에만 보관한다.
- 사용자명 존재 여부를 로그인 오류에서 구분하지 않는다.
- 관리자 권한은 TOTP로 AAL2가 된 활성 관리자에게만 허용한다.

## 오류 처리

- 잘못된 ID 형식: `invalid_login_id`, HTTP 400
- 중복 ID: `login_id_exists`, HTTP 409
- 잘못된 로그인 정보: 일반화된 인증 실패 메시지
- 프로필 누락 또는 내부 이메일 불일치: 로그인 차단 및 설정 오류 화면
- 첫 관리자 중복 실행: 명시적 중단, 기존 계정 변경 없음

## UI 변경

- 로그인: 이메일 라벨·이메일 키보드 설정을 `아이디`와 일반 텍스트 입력으로 교체
- 계정 관리: Gmail 필드를 ID 필드로 교체하고 형식 도움말 표시
- 계정 목록: 이메일 대신 ID 표시·검색
- 상단 프로필: 표시 이름이 없을 때 이메일 대신 ID 사용
- 모바일에서도 입력, 오류 메시지, 버튼에 기존 44px 터치 영역을 유지

## 테스트와 검증

- ID 정규식 경계값과 금지 문자 단위 테스트
- 로그인 ID→가상 이메일 변환 단위 테스트
- 로그인, 재인증, 비밀번호 변경, TOTP 회귀 테스트
- 관리자 계정 생성·중복·권한·보상 삭제 테스트
- DB 트리거, 고유 제약, RLS SQL 테스트
- 첫 관리자 부트스트랩의 최초 실행과 중복 실행 테스트
- 전체 Vitest, ESLint, 프로덕션 빌드 실행
- 새 Supabase 프로젝트에 마이그레이션 적용 후 첫 관리자 로그인과 TOTP 등록 확인
- 데스크톱과 모바일 뷰포트에서 로그인·계정 관리 화면 확인

## 완료 기준

- 사용자가 이메일을 보거나 입력하지 않고 ID와 비밀번호로 로그인한다.
- 모든 신규 계정이 동일한 ID 규칙을 따른다.
- 첫 관리자 계정이 생성되고 TOTP 등록 후 관리자 메뉴에 접근한다.
- 서버 API와 UI에 내부 가상 이메일이 노출되지 않는다.
- 기존 인프라 사용량 화면과 Worker 배포가 새 Supabase·Cloudflare 계정에서 정상 동작한다.
