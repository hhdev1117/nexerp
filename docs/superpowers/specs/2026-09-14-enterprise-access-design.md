# NEXERP 전사 권한등급·직급/직책 매핑 설계

작성일: 2026-09-14. 사용자 승인 방향을 반영한 설계. 적용 대상은 인사뿐 아니라 영업·구매·재고·생산·회계·보고서·시스템 전체다. 이 문서는 구현·운영 적용 완료를 뜻하지 않는다.

## 1. 권한 모델

회사별 레벨 1~5를 기본 등급으로 제공한다. 이름과 권한표, 직급/직책 연결은 회사별로 편집한다. 숫자는 관리상 순서이며 `level >= 4` 같은 조건으로 접근을 허용하지 않는다. 각 등급의 명시적인 권한표가 기준이고 하위 등급의 권한을 자동 상속하지 않는다. 상위 등급을 만들 때 하위 등급 복사를 제공하되 이후 수정은 독립적이다.

| 등급 | 기본 연결 | 권한 프리셋 방향 |
|---|---|---|
| 1 일반 직원 | 사원·대리 | 본인 정보·신청, 배정 업무 메뉴 |
| 2 실무 책임자 | 미배정 | 담당 업무 처리·조회 |
| 3 부서 관리자 | 미배정 | 지정 부서 관리·결재 |
| 4 조직 책임자 | 팀장 | 지정 조직·하위 조직 관리·결재·보고 |
| 5 전사 관리자 | 대표 | 소속 회사 전체 활성 업무 메뉴·전사 조회·관리 |

레벨 2·3은 자동 인사 매핑 없이 제공한다. 직급 명칭만으로 특정 레벨을 추측하지 않는다. 대표 프리셋은 급여 등 민감 업무의 전사 조회를 명시 권한으로 포함하고 화면에 표시한다. 계정·보안·인프라 변경과 권한 부여는 별도 시스템 관리 행동이다. 초기 기술 관리자는 시스템 설정 접근을 유지하되 회사 업무 데이터 권한은 별도로 갖는다.

권한은 `(리소스, 행동, 데이터 범위, 필드 등급)`의 묶음이다. 행동은 menu/read/create/update/cancel/submit/approve/export/close/reopen/manage를 등록형 카탈로그로 관리한다. 범위는 self/assigned/organization/organization_tree/site/company를 사용하며 해당 리소스가 지원하는 범위만 선택할 수 있다.

기본 등급에 구매담당·인사담당·급여담당 등 업무 역할을 더할 수 있다. 사용자별 예외는 allow/deny, 범위, 사유, 유효기간, 부여자를 기록한다. 화면 숨김은 권한 회수가 아니다.

## 2. 직급·직책과 사용자 연결

회사 → 사용자 회사 멤버십 → 직원 연결 → 기준시각 유효한 고용·소속 → 직책/직급 매핑 → 기본 등급 순으로 계산한다. 직원 계정 연결 전에는 권한이 자동 발생하지 않는다.

우선순위는 기간이 있는 명시적 기본등급 지정 > 주 소속의 직책 매핑 > 주 소속의 직급 매핑이다. 매핑이 없으면 자동으로 레벨 1을 부여하지 않고 접근 미배정 상태를 표시한다. 관리자가 검토해 지정한다.

대리가 팀장이면 직책 매핑으로 레벨 4를 받는다. 겸직은 기본등급을 전사 범위로 올리지 않는다. 겸직 직책에서 얻은 권한은 해당 겸직 조직 범위에만 추가하며 근거를 표시한다. 동일 회사의 주 소속·동일 매핑 키·명시적 기본등급 지정에는 유효기간 중복을 금지한다.

승진·보직 변경·퇴사 적용 시각에 기존 자동 권한의 효력이 종료된다. 예약 작업이 늦어져도 요청 시 서버가 유효기간과 고용 상태를 검증한다. 직접 지정한 업무 역할과 예외는 부서 이동 시 재검토 대상으로 표시하되 기존 범위를 자동 확대하지 않는다. 퇴사한 고용 관계에서 파생한 역할은 종료하며 외부 운영자 자격 등 독립 멤버십은 별도 관리한다.

## 3. 최종 권한 판정

1. 활성 사용자·AAL2·회사 멤버십을 검증한다.
2. 모듈 상태와 회사·사업장 경계, 문서 상태 등의 필수 제한을 적용한다.
3. 기본등급·업무 역할·개별 allow에서 요청 행동과 대상 행을 함께 허용하는 권한이 있는지 확인한다.
4. 해당 행동·대상 범위에 일치하는 개별 deny가 있으면 차단한다.
5. 필드 등급과 결재 배정·자기 승인 제한을 검사한다.

허용 권한의 범위를 합칠 때 행동과 범위의 연결을 보존한다. '회사 전체 조회'와 '본인 수정'을 함께 가진 사용자가 회사 전체를 수정할 수 없어야 한다. 범위가 좁은 deny는 해당 범위만 차단한다. 레벨 5도 회사 경계·비활성 모듈·마감·자기 승인 규칙을 우회하지 않는다.

메뉴 표시와 라우터는 동일 정책의 요약을 사용하지만 실제 API/RLS/RPC에서 다시 검증한다. 집계·검색·파일·내보내기도 같은 판정 규칙을 적용한다. 회사 변경·권한 revision 변경 시 브라우저 캐시를 폐기한다. 서비스 키 실행 경로도 호출자·회사·행동을 검증하며 사용자 요청값만으로 우회하지 않는다.

신규 메뉴는 기본 거부한다. 대표가 전체 메뉴를 볼 수 있도록 모듈 설치 시 레벨 5 대표 프리셋에 menu/read 항목을 명시적으로 추가하는 정책 마이그레이션을 포함한다. 사용자 deny는 보존한다. 새 기능의 수정·승인·시스템 관리 행동은 자동 부여하지 않고 설치 권한표에 명시한다.

## 4. 공통 테이블

회사별 업무 행은 company_id와 감사 열·revision을 갖는다. 카탈로그는 전사 정적 정의이며 회사별 정책과 분리한다.

| 테이블 | 주요 내용 |
|---|---|
| `access_resources` | 메뉴·리소스·모듈 연결, 지원 행동·범위·필드 등급 |
| `access_levels` | 회사별 레벨 번호(1~5)·이름·활성 상태, 회사/번호 유일 |
| `access_level_permissions` | level_id, resource, action, scope_kind, field_class |
| `access_position_mappings` | 직급/직책 코드 FK, level_id, valid_from/to, 정책 버전 |
| `access_user_levels` | 사용자별 명시 등급, 유효기간·사유 |
| `access_roles`, `access_role_permissions` | 회사별 업무 역할과 권한 묶음 |
| `access_role_assignments` | 사용자·역할·범위·기간·파생 고용/발령 참조 |
| `access_user_overrides` | 사용자별 allow/deny, 리소스·행동·범위·필드·기간·사유 |
| `access_policy_revisions` | 회사별 발행 버전·작성자·적용 시각 |
| `access_policy_audit` | 변경 전후 정책·행위자·영향 사용자·사유 |

직급·직책 FK는 HR 기준코드를 사용한다. 해당 기준코드·멤버십·계정 연결은 공통 권한의 선행 기반으로 함께 개발하며 HR 메뉴를 닫아도 권한 계산에 필요한 원장은 유지한다. company_id를 포함한 FK로 다른 회사의 역할·직책 연결을 금지한다.

정책 저장·발행은 RPC에서 revision 확인 후 원자적으로 반영한다. 권한 변경 권한과 부여 가능한 최대 범위를 따로 검증한다. 회사 관리자는 다른 회사나 전역 보안 관리 권한을 부여할 수 없다. 자신의 업무등급 수정 권한만으로 시스템 관리자 자격을 만들 수 없다. 마지막 유효 시스템 권한 관리자를 제거하는 변경은 차단한다.

## 5. 관리 화면과 API 계약

시스템 > 권한관리 아래 네 탭을 제공한다.

- **권한등급:** 레벨별 메뉴 트리, 행동 체크, 범위 선택, 민감정보 표시, 등급 복사, 변경 전후 비교.
- **직급·직책 매핑:** 코드·연결 레벨·적용일, 미연결 경고, 변경 영향 사용자 미리보기.
- **사용자 권한:** 자동 기본등급 근거, 업무 역할, 예외 허용·제한, 적용 기간.
- **최종 권한 확인:** 사용자·회사·기준일·메뉴·행동·대상을 지정해 허용 여부와 원인을 표시. 미래 시뮬레이션은 실제 권한을 부여하지 않는다.

예: '홍길동 / 대리·팀장 → 직책 매핑 레벨 4 / 구매1팀 및 하위 조직 / 급여 조회 불가'. 제한·만료·모듈 종료 사유도 설명한다. 사용자별 권한 미리보기 자체는 관리 권한으로 보호한다.

리포지토리 계약: listLevels, getLevelPermissions, saveLevelPermissions, listPositionMappings, savePositionMapping, getUserAssignments, saveUserAssignments, previewPolicyChange, publishPolicy, explainAccess. 쓰기는 expectedRevision/requestId를 받고 변경 사유를 필수로 한다. 최종 적용과 preview 사이에 사용자·조직·정책 revision이 바뀌면 재검토를 요구한다.

## 6. 기존 권한에서 전환

현재 `admin/approver/user`, role_menu_permissions, accessStore의 admin 무조건 허용, hasRole 버튼, authGuard와 DB의 is_admin을 모두 조사 대상에 포함한다. 메뉴만 바꾸고 서버 권한을 그대로 두는 전환은 완료로 인정하지 않는다.

1. 공통 카탈로그·정책 엔진·회사 멤버십·최소 직원/직급/직책 연결을 먼저 추가한다.
2. 현재 역할·메뉴 권한과 실제 사용자 목록을 읽어 이전안을 만든다. 기존 admin을 자동 대표로 간주하지 않고 기술 관리자 자격은 보존한다. 사용자 회사 소속·직급은 추정하지 않는다.
3. 누락된 회사·직원 연결을 관리 화면에서 지정하고 이전 전후 권한 차이를 확인한다. 새 권한 범위를 정할 수 없는 계정은 활성 전환 대상에서 제외한다.
4. 실제 권한에 영향을 주지 않는 비교 판정으로 현재 동작과 차이를 수집한다. 권한 확장·회수와 필수 업무 접근을 검토한다.
5. 모듈별로 메뉴·라우터·API·RLS·RPC를 함께 전환한다. 전환한 모듈에는 기존 role 허용을 OR 조건으로 남기지 않는다. 미전환 모듈만 기존 정책을 유지한다.
6. 전체 모듈 전환과 회귀 검증 후 legacy 메뉴 정책·역할 분기를 폐기한다. 감사·마이그레이션 이력은 보존한다.

전환 실패 시 해당 모듈의 신규 쓰기를 중지하고 검증된 정책 revision으로 되돌린다. 새 데이터에 과거의 넓은 권한을 자동 복구하지 않는다. 이미 변경된 데이터·이력은 유지한다.

## 7. 인수 기준

- 사원·대리 레벨 1, 대리+팀장 레벨 4, 대표 레벨 5 매핑이 정상 작동한다.
- 대표는 소속 회사 전체 활성 업무 메뉴와 허용된 전사 정보를 보고, 다른 회사 정보는 접근하지 못한다.
- 레벨 1 급여담당은 부여된 급여 업무를 수행하고, 급여 역할이 없는 레벨 4 팀장은 동료 급여를 읽지 못한다.
- 개별 deny는 같은 대상의 allow보다 우선한다. 회사조회+본인수정 권한 조합이 회사수정으로 확대되지 않는다.
- 겸직·예정 발령·팀장 해제·기간 만료·퇴사에서 권한이 정해진 시각과 범위대로 바뀐다.
- 매핑이 없는 직원은 임의 권한을 받지 않는다. 마지막 권한 관리자 제거·회사 밖 권한 부여를 차단한다.
- 직접 URL·RPC·검색·보고서·내보내기·파일 다운로드에도 권한이 강제된다.
- 기존 계정·MFA·회사/사업장·업무 메뉴의 권한 전환 차이를 설명할 수 있다.

## 8. 개발 단위

첫 개발은 공통 카탈로그·회사 멤버십·등급/업무 역할·판정 엔진과 DB 정책이다. 다음으로 최소 인사 기준코드·계정 연결·직급/직책 매핑, 네 관리 화면, 기존 전사 모듈의 권한 이전을 진행한다. 인사 전체 설계의 1단계에 포함하고 이후 인사·급여 등 신규 모듈은 이 공통 정책만 사용한다.
