# 재입사·고용 회차 관리 설계

**기준일:** 2026-09-15
**범위:** 인사 기본 모듈(`hr.core`)의 직원 원장, 발령, 계정 연결, 권한 판정

## 목적

직원을 새로 만들거나 기존 기록을 덮어쓰지 않고 동일 직원 아래에 최초 입사와 재입사를 독립된 고용 회차로 보존한다. 현재 재직 상태와 직급·직책은 유효한 최신 회차에서만 계산하며, 과거 회차의 발령·퇴사·계정 연결 감사 기록은 변경하지 않는다.

## 데이터 모델

`hr_employment_cycles`를 추가한다.

| 필드 | 의미 |
|---|---|
| `id` | 고용 회차 식별자 |
| `company_id`, `employee_id` | 회사와 직원 |
| `sequence_no` | 직원별 1부터 증가하는 회차 |
| `hire_date` | 해당 회차 입사일 |
| `end_date` | 퇴사 발효일, 즉 첫 비재직일. 예정 또는 확정 퇴사가 없으면 null |
| `site_id`, `department`, `grade`, `position` | 회차 시작 시점 소속 |
| `reason`, 생성·수정 작업자와 시각 | 감사 정보 |
| `revision` | 동시 수정 충돌 방지 |
| `cancelled_at`, `cancelled_by`, `cancellation_reason` | 미래 재입사 회차 취소 이력 |

기존 직원은 마이그레이션 시 회차 1로 이전한다. 기존 `hr_employees.hire_date`와 시작 소속을 사용하고, 가장 이른 유효 퇴사 발령을 `end_date`로 반영한다. 기존 발령에는 `employment_id`를 채워 회차 1에 연결한다. 이후 모든 발령은 현재 또는 예정된 대상 회차를 명시한다.

`hr_employees`는 동일인을 나타내는 직원 마스터로 유지한다. 사번과 이름, 선택적 로그인 계정은 직원 단위다. 기존 `hire_date`와 시작 소속 컬럼은 호환성을 위해 남기되 신규 판정은 고용 회차를 기준으로 한다. 외부 API 응답의 `hireDate`, 현재 소속, 상태는 유효한 최신 회차에서 계산한다.

## 상태와 날짜 규칙

서울 날짜를 기준으로 회차 상태를 계산한다.

- `planned`: 입사일이 오늘보다 뒤
- `active`: 입사일이 오늘 또는 이전이고, 퇴사 발효일이 없거나 오늘보다 뒤
- `terminated`: 퇴사 발효일이 오늘 또는 이전
- `cancelled`: 발효 전 취소되어 권한·기간 판정에서 제외

직원별 고용 회차 기간은 겹칠 수 없다. 재입사는 최신 회차에 유효한 퇴사 발령이 있을 때만 등록하며 재입사일은 퇴사 발효일 이후여야 한다. 당일 퇴사 후 당일 재입사는 허용하지 않는다. 미래 퇴사가 예약되어 있으면 그 다음 날짜 이후의 재입사를 예약할 수 있다.

재입사 예약 뒤 기존 퇴사 발령을 취소하면 기간이 겹치므로 취소를 차단한다. 재입사 회차를 취소한 뒤에만 퇴사 발령을 취소할 수 있다. 시작일이 오늘 또는 과거인 고용 회차는 삭제하거나 취소하지 않는다.

## 발령과 계정 권한

`private.hr_employee_state`는 오늘 유효한 회차를 선택하고 그 회차의 최신 적용 발령을 합성한다. 유효한 회차가 없으면 접근 권한을 부여하지 않는다. 따라서 미래 재입사 등록만으로 계정 접근이 열리지 않으며 재입사일부터 직급·직책 매핑과 소속 범위가 자동 적용된다.

퇴사 상태에서 기존 계정 연결은 감사 목적으로 유지할 수 있다. 재입사 등록 화면에서 연결 가능한 계정을 선택적으로 연결·교체할 수 있으며 저장 전 적용 예상 레벨을 표시한다. 직원에 연결된 계정은 회사별로 계속 유일해야 한다. 발행 정책의 직접 레벨·역할·개별 권한은 기존 우선순위를 유지한다.

재입사 후의 전보·직급·직책 변경과 퇴사 발령은 새 고용 회차에 연결한다. 이전 회차 발령은 조회만 가능하다. 직원 기본정보 정정에서 입사일은 제거하고, 회차별 입사일 정정은 이번 단계에서 제공하지 않는다. 기존 회차 1 입사일 정정 이력은 그대로 보존하며 신규 이름 정정 감사 문서에도 기존 호환을 위해 최초 입사일을 변경 없이 포함한다.

재입사 문서의 계정 처리는 `accountMode`으로 구분한다. `keep`은 기존 연결 유지, `unlink`는 연결 해제, `replace`는 선택한 후보 계정으로 교체한다. 변경이 생기면 007의 계정 연결 감사 테이블에도 같은 사유와 작업자를 기록한다.

## RPC와 권한

다음 RPC를 추가한다.

- `hr_employment_history(company, employee)`: 회차별 시작 소속, 입사·퇴사일, 상태, 발령 목록 조회
- `hr_prepare_rehire(company, employee)`: 재입사 가능 여부, 가장 이른 재입사일, 기준정보, 계정 후보와 예상 레벨 조회
- `hr_create_reemployment(company, employee, employee_revision, document, reason)`: 새 회차와 선택적 계정 연결을 한 트랜잭션으로 생성
- `hr_cancel_planned_employment(company, employee, employment, employee_revision, reason)`: 미래 재입사 회차 취소

조회에는 `hr.core/read/company`, 생성·취소에는 `hr.core/update/company`가 필요하다. 재입사 생성은 인사 모듈 상태가 `enabled`일 때만 허용한다. 미래 회차 취소는 `enabled`와 `draining`에서 기존 원래 수정 권한이 있는 담당자에게 허용한다. `read_only`, `disabled`에서는 변경을 차단한다.

재입사 생성과 취소는 회사 행, 직원 행 순서로 잠가 모듈 상태 변경·발령 변경과 경합 순서를 통일한다. 예상 직원 버전과 서버의 최신 회차를 다시 검사한다. 사유는 1~2000자로 제한하고 원문 DB 오류는 클라이언트에 노출하지 않는다.

## 인사 모듈 중지와 예약 작업

미래 재입사 회차는 예정 발령과 같은 미처리 작업이다. `private.hr_module_pending`에 취소되지 않은 미래 고용 회차 수를 포함한다. 예정 재입사가 있으면 `read_only` 또는 `disabled`로 바로 전환할 수 없고, 재입사일을 기다리거나 `enabled` 또는 `draining` 상태에서 예정 회차를 취소해야 한다.

## 화면

직원 상세에 **고용 이력** 타임라인을 추가한다. 각 회차는 회차 번호, 입사일, 퇴사일, 시작 소속, 현재 상태와 해당 회차의 발령을 표시한다. 최신 퇴사 회차가 있는 직원에게만 **재입사 등록** 버튼을 노출한다.

재입사 화면은 입사일, 사업장, 부서·직급·직책, 선택적 로그인 계정, 사유를 받는다. 모든 입력에 화면 라벨을 연결하고 저장 중 상태와 필드 가까이 오류를 표시한다. 검토 단계에서 이전 퇴사일, 새 입사일, 계정 전후, 예상 권한 레벨을 한 번 더 보여준다. 375px에서는 한 열, 넓은 화면에서는 두 열로 배치하며 가로 스크롤을 만들지 않는다.

## 오류 처리

- 다른 작업이 먼저 저장: 최신 직원·고용 이력을 다시 불러오도록 안내
- 퇴사 없는 직원, 기간 중복, 잘못된 기준정보: 저장 거절 후 해당 조건 안내
- 계정 중복 또는 정책 후보 제외: 계정을 다시 선택하도록 안내
- 재입사 예약이 있는 상태에서 퇴사 취소: 예약 회차를 먼저 취소하도록 안내
- 회사·사용자 변경 중 늦게 도착한 응답: 화면에 반영하지 않음

## 검증

실제 001~007 마이그레이션과 기존 직원·퇴사·계정 연결 데이터를 사용해 008을 검증한다. 기존 데이터 이전, 과거·미래 퇴사, 예약·활성 재입사, 기간 중복, 권한 활성 시점, 발령의 회차 분리, 계정 중복, 모듈 중지, 버전 충돌, RLS와 감사 이력을 포함한다.

프런트엔드는 저장소 응답 검증, 오류 정제, 사용자·회사·직원 전환 시 오래된 응답 폐기, 검토 단계, 모바일 레이아웃을 테스트한다. 전체 Vitest, ESLint, 프로덕션/PWA 빌드와 1440px·375px 실제 렌더링을 완료한다. 운영 DB 적용과 배포는 별도 승인 범위다.
