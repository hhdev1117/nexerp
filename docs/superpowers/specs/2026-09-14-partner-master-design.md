# 거래처 통합 기준정보 설계

## 목표

영업의 고객사와 구매의 공급업체를 하나의 거래처 원장으로 통합한다. 거래처는 회사별로 관리하며 고객, 공급업체 또는 두 역할을 동시에 가질 수 있다. 영업·구매 업무 화면은 거래처를 직접 관리하지 않고 이 원장을 조회하고 선택한다.

이번 구현 범위는 거래처 기준정보의 데이터베이스, 접근 제어, 저장소, 상태 관리, 관리 화면, 메뉴 통합과 기존 권한 이전까지다. 품목 기준정보와 영업·구매 전표 연결은 다음 작업에서 같은 패턴으로 진행한다.

## 사용자 흐름

- 모든 활성 사용자는 `기준정보 > 거래처 관리`에서 현재 회사의 거래처를 조회하고 검색할 수 있다.
- 관리자는 거래처를 등록하고 수정하고 비활성화하거나 다시 활성화할 수 있다.
- 일반 사용자와 결재자는 관리 버튼과 입력 폼을 볼 수 없다.
- 거래처 등록 시 고객과 공급업체 중 하나 이상을 반드시 선택한다.
- 영업의 기존 `/sales/customers`와 구매의 기존 `/purchasing/vendors` 주소로 접근하면 `/master/partners`로 이동한다.
- 메뉴에는 중복 항목을 표시하지 않고 `기준정보 > 거래처 관리`만 표시한다.

## 데이터 모델

`public.partners` 테이블을 추가한다.

| 열 | 규칙 |
|---|---|
| `id` | UUID 기본 키 |
| `company_id` | `companies.id` 참조, 삭제 제한 |
| `code` | 회사 안에서 고유한 대문자 코드, 2~20자 |
| `name` | 필수 거래처명 |
| `business_number` | 선택, 숫자 10자리, 회사 안에서 값이 있을 때 고유 |
| `is_customer` | 고객 역할 여부 |
| `is_vendor` | 공급업체 역할 여부 |
| `representative` | 대표자명, 선택 |
| `email` | 담당 이메일, 선택 |
| `phone` | 대표 전화, 선택 |
| `address` | 주소, 선택 |
| `is_active` | 활성 상태, 기본값 `true` |
| 감사 열 | 기존 회사·사업장과 동일한 생성/수정 시각 및 사용자 |

제약 조건은 역할 하나 이상 선택, 빈 이름 금지, 코드 형식, 사업자등록번호 형식을 데이터베이스에서도 강제한다. 물리 삭제 권한은 부여하지 않는다.

## 회사 범위와 접근 제어

단일 법인 전용 배포지만 여러 회사 원장을 지원하므로 거래처는 항상 `company_id`를 가진다. 사용자가 현재 회사를 선택하지 않은 초기 상태에서는 화면이 첫 번째 활성 회사를 기본 선택하며, 화면의 회사 선택기로 조회 범위를 바꿀 수 있다.

RLS는 다음과 같다.

- MFA AAL2를 통과한 활성 사용자는 활성 여부와 관계없이 거래처를 조회할 수 있다.
- MFA AAL2를 통과한 활성 관리자만 등록과 수정이 가능하다.
- 거래처가 연결되는 회사가 비활성 상태라면 활성 거래처를 새로 만들거나 다시 활성화할 수 없다.
- 클라이언트가 보낸 감사 열은 트리거가 실제 호출자 정보로 덮어쓴다.

## 애플리케이션 구조

기존 master 계층을 확장한다.

- `src/repositories/master/supabaseMasterRepository.js`: 거래처 목록·등록·수정 메서드와 DB-UI 필드 매핑
- `src/repositories/master/demoMasterRepository.js`: Supabase 미설정 개발 환경용 동일 계약
- `src/stores/master.js`: `partners`, 회사별 필터, 등록·수정 상태 반영
- `src/views/master/Partners.vue`: 검색, 회사 필터, 역할·상태 필터, 테이블, 관리자 편집 대화상자
- `src/data/erp.js`: 중복 고객·공급업체 메뉴 제거, `master.partners` 명칭을 `거래처 관리`로 변경
- `src/router/index.js`: 전용 화면 연결 및 두 기존 주소의 호환 리다이렉트

저장소 메서드는 `listPartners`, `createPartner`, `updatePartner`로 고정한다. 부분 수정은 전달된 필드만 DB 열로 변환해 다른 값을 덮어쓰지 않는다.

## 권한 이전

새 마이그레이션은 `role_menu_permissions`에 저장된 기존 권한을 보존한다.

- 역할이 `sales.customers`, `purchasing.vendors`, `master.partners` 중 하나라도 허용받았다면 `master.partners`를 허용한다.
- 제거된 두 메뉴 키는 권한 테이블에서 삭제한다.
- 관리자 고정 접근 정책은 바꾸지 않는다. 거래처 메뉴는 역할별 메뉴 권한으로 노출하되 실제 쓰기는 RLS가 관리자에게만 허용한다.

## 오류와 검증

- 중복 코드는 `duplicate_code`, 중복 사업자등록번호는 `duplicate_business_number`로 구분한다.
- 비활성 회사에 활성 거래처를 저장하면 `company_inactive`로 안내한다.
- 필수 역할, 코드, 이름, 이메일, 사업자등록번호는 저장 전에 화면에서 검증하고 첫 오류 입력란으로 포커스를 이동한다.
- 네트워크나 권한 오류의 원문은 사용자에게 노출하지 않고 기존 master 오류 매핑을 사용한다.

## 테스트

구현은 TDD로 진행한다.

- 메뉴 테스트: 중복 메뉴 제거, 새 메뉴 정의, 기존 주소 리다이렉트
- 마이그레이션 정적 테스트: 테이블·제약·인덱스·RLS·정책·감사 트리거·권한 이전 SQL
- 저장소 테스트: 필드 매핑, 정렬, 부분 수정, 오류 매핑
- 스토어 테스트: 회사별 조회, 정렬, 생성·수정 반영
- 화면 마운트 테스트: 필터, 검증, 관리자 편집, 일반 사용자 조회 전용
- Docker 사용 가능 환경의 pgTAP: 관리자 쓰기, 사용자 읽기, 회사 격리 조건과 비활성 회사 규칙
- 전체 Vitest, ESLint, 프로덕션 빌드, `git diff --check`

## 배포 순서

1. 실패하는 단위·화면·마이그레이션 테스트를 먼저 추가한다.
2. 마이그레이션과 애플리케이션을 구현해 테스트를 통과시킨다.
3. 호스팅 Supabase에 마이그레이션을 적용하고 카탈로그를 검증한다.
4. Cloudflare Worker를 배포하고 `/api/health` 및 운영 라우팅을 확인한다.
5. `HANDOFF.md`를 갱신하고 커밋한 뒤 GitHub `main`에 푸시한다.

호스팅 DB 변경은 적용 직전에 SQL 내용과 영향을 다시 보고하고 사용자 승인을 받은 뒤 수행한다.
